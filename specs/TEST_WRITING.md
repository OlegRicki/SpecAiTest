# Рекомендации к написанию тестов

Этот файл — правила для агента и людей: **как писать автотесты** после проверки функциональности сайта.

Рабочий каталог тестов: `tests/{PROJECT}/` (`PROJECT` в `.env`).
`INDEX.md` текущего проекта (`specs/{PROJECT}/INDEX.md`) — только карта разделов и статусы; URL/логин/пароль из `.env`.

---

## Базовый промпт (использовать после ручного/агентного прогона UI)

```text
Создай теперь детерминированный тест или набор тестов, которые будут проверять
работоспособность этой функциональности вэб-сайта, которую ты сейчас проверил.
Используй Python и uv для работы с Python Проектом. Используй современную версию Python
- 3.14, а для тестов используй pytest. Также используй паттерн PageObject. Тесты должны быть нехрупкими, то есть, например,
не полагайся на порядок полей в форме, который может меняться. Реализовав тесты,
убедись, что они работают и проходят
```

Если есть раздел документа со сценариями, добавляйте в конец:

```text
Сценарии: specs/{PROJECT}/scenarios/<файл>.md
В docstring каждого теста укажи ID вида «TC-x.y — …»
После написания запусти: uv run pytest -q <новые_файлы>
Обнови статус раздела в INDEX.md текущего проекта (specs/{PROJECT})
```

## Стек (обязательно)

| Что | Как |
|-----|-----|
| Python | **3.14** |
| Пакеты / venv | **uv** (`uv add`, `uv run`) |
| Тесты | **pytest** |
| Отчёты | **Allure** — шаги/скриншоты/данные автоматически через `conftest.py` + `allure_report.py` |

Запуск:

```bash
uv run pytest -q
uv run pytest -q tests/<project>/test_login.py
```

## Нехрупкие тесты — правила

1. **Не полагаться на порядок** полей, кнопок, строк таблицы.
2. Искать элементы по стабильным признакам:
   - `name`, `id`, `role`, текст кнопки/лейбла
   - `get_by_role`, `get_by_label`, `locator('[name="username"]')`
3. **Не использовать** хрупкое:
   - `nth(0)`, `nth(1)` без необходимости
   - длинные CSS вроде `div > form > div:nth-child(2) input`
   - XPath от позиции в DOM
4. Ждать состояние, а не «поспать и надеяться»:
   - `expect(...).to_be_visible()`
   - `wait_for_load_state` / ожидание URL / текста
5. Один тест = одна проверка поведения (или маленький связанный набор в классе).
6. Общие URL, логин, пароль — в `conftest.py` / env, не копипаста по файлам.
7. Тесты должны быть **детерминированными**: при тех же данных стенда — тот же результат.
   **Лимит попыток в автотестах:** для каждого набора параметров сценария максимум 2 попытки за один запуск pytest (первый запуск + один повтор после сбоя), включая все обёртки и pytest rerun. После успеха сразу завершать тест; после второй неудачи завершать ошибкой с диагностикой. Не умножать попытки вложенными циклами; запрет повторов в сценарии означает одну попытку. При обновлении раздела привести существующие тесты к этому правилу. Число исследовательских запусков и повторных запусков pytest при разработке не ограничивается; внутри каждого запуска автотеста лимит сохраняется.
8. **Загрузка файлов:** как Selenium `send_keys(path)` — `upload_file(page, path)` из `conftest` / `set_input_files`. **Не кликать** по `input[type=file]`.
9. **Allure:** каждый выполняемый шаг сценария оформлять через `allure.step` с номером и понятным названием из актуального документа. Автоматические действия Playwright оставлять вложенными. Указывать название кнопки/поля и ожидаемое состояние; не оставлять безымянные «Нажать элемент» / «Проверить элемент». В общем шаге заполнения формы отдельно называть каждое поле. Docstring с `TC-x.y — …` задаёт заголовок теста, но не заменяет шаги.
   Каждую повторную попытку группировать в `allure.step("Попытка N/M")`. При сбое прикладывать скриншот и фактическое состояние до следующей попытки, включая перехватываемые исключения. Ошибка должна описывать невыполненное ожидание и фактический результат, без предположений о причине. Не прикладывать пароли и токены.
   При обновлении раздела проверять оформление и существующих тестов. После запуска просмотреть соответствующие `allure-results/*-result.json`: названия шагов, вложенность попыток и диагностику сбоев. Не ослаблять проверки ради оформления отчёта.
10. **Чат / LLM:** если в сценарии есть **Проверка LLM:** — UI проверяй Playwright’ом, смысл ответа — `from llm_judge import assert_chat_quality` (маркер `@pytest.mark.llm`). Без LLM тест skipped, в Allure тег `llm-unavailable`. Кейсы без этого блока не менять.

## Структура теста

Как в `selenium-tests`, разделяй код на три слоя:

1. `tests/{PROJECT}/locators/` — именованные локаторы по страницам или частям
   интерфейса. Для Playwright можно использовать функции, возвращающие
   `Locator`. Значения, от которых зависит поиск, передавай аргументами.
2. `tests/{PROJECT}/pages/` — классы Page Object. Они используют локаторы,
   выполняют действия Playwright и проверяют состояние интерфейса. Методы
   называй по смыслу, например `sign_in` или `open_data_tab`.
3. `tests/{PROJECT}/test_*.py` — данные, порядок шагов Allure, ожидаемый результат
   и вызовы методов Page Object. По тесту должно быть видно, что именно
   проверяется. Если сценарий описывает ввод логина и нажатие отдельными
   шагами, сохрани оба шага в тесте и используй отдельные методы.

Добавь `__init__.py` в `locators/` и `pages/`. При обновлении одного кейса
используй существующие модули и не реорганизовывай соседние тесты.

`tests/{PROJECT}/locators/auth.py`:

```python
from playwright.sync_api import Locator, Page


def username_field(page: Page) -> Locator:
    return page.get_by_label("Имя пользователя", exact=True)


def password_field(page: Page) -> Locator:
    return page.get_by_label("Пароль", exact=True)


def login_button(page: Page) -> Locator:
    return page.get_by_role("button", name="Войти", exact=True)
```

`tests/{PROJECT}/pages/auth_page.py`:

```python
from playwright.sync_api import Page, expect

from locators.auth import login_button, password_field, username_field


class AuthPage:
    def __init__(self, page: Page):
        self.page = page

    def open(self, address: str) -> None:
        self.page.goto(address)

    def sign_in(self, username: str, password: str) -> None:
        username_field(self.page).fill(username)
        password_field(self.page).fill(password)
        login_button(self.page).click()

    def expect_redirect_to(self, address: str) -> None:
        expect(self.page).to_have_url(address)
```

`tests/{PROJECT}/test_login.py` (пример высокого уровня):

```python
import allure

from pages.auth_page import AuthPage


def test_successful_sign_in(page, base_url, login_credentials):
    """TC-1.1 — успешный вход."""
    auth = AuthPage(page)
    with allure.step("1. Открыть страницу входа"):
        auth.open(base_url)
    with allure.step("2. Войти с выданными учётными данными"):
        auth.sign_in(**login_credentials)
    with allure.step("3. Проверить возврат на исходный адрес"):
        auth.expect_redirect_to(base_url)
```

- Имена тестов — поведение, не `test1`
- Docstring — ID кейса (TC-…), если есть
- Файл: `tests/test_<раздел>.py`
- Все кейсы одного раздела размещать в одном `tests/{PROJECT}/test_<раздел>.py`. Новые кейсы добавлять в существующий файл раздела; общие вспомогательные функции можно выносить отдельно. При объединении файлов не оставлять дубликаты тестов.

## Порядок работы агента

HEADLESS из окружения обязателен также при исследовании. Не переключать режим для диагностики: при TRUE запрещены `headless=False` и `--headed`. При FALSE использовать `headless=False`, `args=["--start-maximized"]` и `browser.new_context(no_viewport=True)`, как в `tests/conftest.py`. При ограничении режима сообщить о нём.

Пайплайн выполняет предварительный pytest по каждому кейсу и сравнивает отпечаток его требований. Проходящие тесты с неизменившимися требованиями сохраняются без вызова агента. При первом запуске без истории проходящие тесты принимаются за исходную версию (это не аудит полноты покрытия). Если передан один кейс, работать только с ним, не менять соседние тесты и не выставлять `done` всему разделу. Итог агента записывать в JSON по указанному в промпте пути; статусы кейсов и раздела рассчитывает пайплайн. Перед правками сохраняется копия Python-кода тестов. При неуспешной проверке откатываются изменения текущего кейса и затронутых им общих функций; ранее сохранённые исправления других кейсов остаются. При изменении общих функций результаты соседних тестов сравниваются до и после: прежнее падение не является регрессией, новое падение ранее проходившего теста — причина отката текущих изменений.

Если пайплайн сообщает об изменении требований, разрешено удалять и заменять устаревшие варианты параметризации только текущего кейса. Покрыть все строки и режимы актуального сценария; не сохранять старые значения, которых в нём больше нет. Описать изменение наборов в итоговом reason. При неизменившихся требованиях удалять варианты ради прохождения запрещено.

При настройке модели меняй только параметры, для которых сценарий задаёт значение или режим, включая значения из таблиц. Для остальных сохраняй исходное состояние нового узла. Не выбирай варианты по обрезанным подписям и не меняй параметры ради успешного расчёта.

Если актуальные тесты полностью реализованы и воспроизводят дефект приложения, вернуть `blocked`, `failure_kind: application`, `coverage_complete: true` и `application_failures` (точный pytest nodeid каждого падающего варианта → дословное сообщение UI/сервера, включённое в AssertionError). В reason описать воспроизведение и доказательства. Пайплайн сверит данные с независимым прогоном и сохранит актуальные тесты со статусом blocked, если нет новых регрессий соседних кейсов. Не классифицировать ошибки Python/локаторов, тайм-ауты, недоступность стенда, пропуски или неполное покрытие как подтверждённый дефект приложения ради обхода отката.

При обновлении существующих тестов сначала сравнить код с актуальным сценарием и сразу сохранить исправления, не требующие исследования UI: номера шагов, лимиты ожиданий и повторов, удаление проверок, не предусмотренных сценарием. Затем исследовать неизвестные элементы и состояния. Сохранять изменения по мере работы, а не только после завершения всего исследования. При блокирующей проблеме сохранить сделанные исправления, указать причину и поставить `blocked`; обязательную проверку не заменять пропуском или фиктивным успехом. Количество исследовательских запусков не ограничивать.

В тестах и исследовательских скриптах ждать состояние UI с конечным тайм-аутом, а не использовать длительный фиксированный `sleep`. Учитывать единицы: `time.sleep` принимает секунды, `page.wait_for_timeout` — миллисекунды.

1. Исследует функциональность в браузере. Для всех параметризованных сценариев любого проекта (таблицы, списки наборов данных, режимы) сначала выбирает один представительный набор с наиболее полным набором полей и действий и исследует его во всех применимых режимах. Остальные наборы сравнивает по требованиям; дополнительно исследует только неизвестные отличия. Не требуется предварительно проходить каждую комбинацию перед написанием тестов. Количество исследовательских запусков не ограничено.
2. Пишет pytest-тесты по правилам этого файла для всех предусмотренных сценарием комбинаций параметров и режимов, а не только исследованного набора.
3. Запускает `uv run pytest` для всех этих комбинаций. При падениях исследует конкретную проблему и исправляет тест без ослабления требований. При дефекте приложения сохраняет диагностику и ставит `blocked`.
4. Не считает задачу сделанной, если тесты не запускались.
