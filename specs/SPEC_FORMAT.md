# Рекомендации по написанию тест-документа

Документ для **человека**, который описывает, *что и как проверять* на сайте
(аналитик, тестировщик, автор методики испытаний).

Цель — чтобы другой человек (или автотесты) мог **однозначно воспроизвести** проверку:
что сделать → что должно получиться.

---

## Зачем так писать

Хороший документ:
- понятен без автора рядом;
- разбит на логичные части (не «простыня»);
- у каждого пункта есть **ожидаемый результат**;
- шаги конкретные: кнопки, поля, роли, данные.

Плохой документ:
- «проверить, что всё работает»;
- шаги только скриншотами без текста;
- нет ID у проверок;
- непонятно, с какой учёткой и на каком стенде работать.

---

## Структура документа

Держите три уровня:

1. **Документ** — название документа / объект испытаний
2. **Раздел** — тема или блок функциональности (Авторизация, Заявки, Роли…)
3. **Проверка (кейс)** — одна законченная проверка с шагами и ожиданием

Так удобно читать, согласовывать и закрывать по частям.

В Word:
- название документа — стиль **Заголовок 1**
- разделы — **Заголовок 2**
- отдельные проверки — **Заголовок 3**

В Markdown то же через `#` / `##` / `###`.

---

## Как нумеровать

### Разделы
`1. Авторизация`, `2. Создание заявки`, `3.1 Поиск`

Номер + короткое понятное имя.

### Проверки (обязательно свой ID)
`TC-1.1 Успешный вход`, `TC-2.3 Создание без обязательного поля`

Зачем ID:
- на него ссылаются в баг-репортах и автотестах;
- проще сказать «не проходит TC-2.3», чем «тот про заявку в середине документа».

ID не меняйте без необходимости. Название кейса можно уточнять.

---

## Шаблон одной проверки

Каждый кейс лучше писать одинаково:

**Название:** `TC-1.1 Успешный вход`

**Предусловия** — что должно быть до начала:
- авторизован пользователь или нет.
- необходимые шаги

**Шаги** — что сделать, по порядку:
1. одно действие = один шаг;
2. пишите видимые названия: кнопка «Войти», поле «Пароль», пункт меню «Заявки»;
3. указывайте, *что ввести*, если важны конкретные значения.

**Ожидание** — как понять, что проверка прошла:
- конкретный текст, статус, URL, появление/исчезновение элемента;
- можно несколько пунктов списка.

**Примечания** (по желанию) — ограничения стенда, известные баги, «пока не автоматизировать».

**Проверка LLM** (только для чата / свободного текста) — критерии смысла ответа, не дословная цитата. UI-ожидание пишите в **Ожидание**. Нет этого блока — кейс полностью обычный.

```text
Проверка LLM:
- Ответ по теме вопроса
- Нет голого отказа без объяснения
```

### Пример

```text
TC-1.1 Успешный вход

Предусловия:
- Пользователь не авторизован
- Тестовая учётная запись настроена в локальном окружении

Шаги:
1. Открыть страницу входа
2. Ввести логин в поле «Имя пользователя» (username)
3. Ввести пароль в поле «Пароль»
4. Нажать кнопку «Войти»

Ожидание:
- Открыта страница после входа (не форма логина)
- Пользователь считается авторизованным
```

---

## Как писать шаги

| Лучше | Хуже |
|-------|------|
| Нажать кнопку «Создать заявку» | Нажать нужную кнопку |
| Ввести в поле «Сумма» значение `100` | Заполнить форму |
| Открыть раздел «Заявки» в меню | Перейти куда надо |
| Выбрать в списке статус «Новая» | Выбрать статус |

Не смешивайте в одном шаге действие и проверку.
Сначала действия в **Шагах**, результат — в **Ожидании**.

---

## Как писать ожидание

Ожидание должно быть **проверяемым** другим человеком без догадок.

| Лучше | Хуже |
|-------|------|
| Статус заявки = «Новая» | Заявка создалась нормально |
| Показано сообщение «Неверный пароль» | Ошибка |
| URL содержит `/dashboard` | Открылась нужная страница |
| Кнопка «Удалить» недоступна (disabled) | Права работают |

Если ожиданий несколько — списком.
Если «не должно произойти» — пишите явно: «заявка не создана», «остаёмся на форме входа».

---

## Предусловия и зависимости

- По возможности делайте кейс **самостоятельным**.
- Если кейсу нужна сущность из другого кейса — напишите в предусловиях:
  «Существует заявка, созданная по TC-3.1»
  или «В системе есть пользователь с ролью Оператор».
- Не полагайтесь на «и так понятно, что мы уже залогинены» — укажите.

Отдельно в начале документа (или в блоке окружения) опишите:
- URL стенда;
- тестовые учётки и роли;
- что нельзя трогать на стенде (прод-данные и т.п.).

Пример блока окружения:

```text
Окружение
- Роль для основных проверок: Пользователь
- Браузер: Chrome / Chromium
```

## Как дробить большой документ

Не делайте один раздел «Всё подряд» на 50 проверок.

Лучше:
- `1. Авторизация`
- `2. Главная`
- `3. Заявки — создание`
- `4. Заявки — поиск и фильтры`
- `5. Роли и права`

В одном разделе обычно комфортно **до ~10–15 кейсов**.
Если больше — дробите тему дальше (`3.1`, `3.2`).

Так документ удобнее согласовывать, тестировать и принимать по частям.

---

## Формулировки, которых лучше избегать

- «Проверить корректность работы модуля»
- «Убедиться, что система функционирует должным образом»
- «Аналогично предыдущему пункту» — без копирования шагов
- Только скриншот без текстовых шагов и ожидания
- Кейс без ID и без ожидания

---

## Чеклист автора перед сдачей документа

- [ ] Есть название документа и понятные разделы
- [ ] У каждой проверки есть ID (`TC-…`) и короткое имя
- [ ] У каждой проверки есть шаги и ожидание
- [ ] Указаны стенд, роли, нужные данные
- [ ] Ожидания конкретные, без «всё ок»
- [ ] Зависимые кейсы явно ссылаются на предусловия
- [ ] Разделы не слишком огромные

---

## Пример оглавления небольшого документа

```text
Приёмка веб-приложения

Окружение
- URL: …
- Учётки: …

1. Авторизация
   TC-1.1 Успешный вход
   TC-1.2 Пустой пароль
   TC-1.3 Неверный пароль

2. Главная страница
   TC-2.1 Отображение заголовка и основных блоков

3. Заявки
   TC-3.1 Создание заявки с обязательными полями
   TC-3.2 Создание без обязательного поля
   TC-3.3 Поиск заявки по номеру
```

Этого достаточно, чтобы человек мог пройти проверки руками, а команда автоматизации — перенести их в автотесты без уточняющих созвонов на каждый пункт.

---

## В каком файле отдавать документ

Удобные варианты:
- **Word (.docx)** — с заголовками 1/2/3;
- **Markdown (.md)** — та же структура;
- **PDF** — только если это **текстовый** PDF (не скан/картинка). Структура та же: название, разделы, кейсы `TC-…`, шаги и ожидания текстом.

Скан PDF без текстового слоя для автоматизации не подходит — нужен OCR или исходник в Word/Markdown.
