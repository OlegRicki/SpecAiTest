# Правила для агента

## Источник сценариев
- Имя проекта задаётся в `.env`: `PROJECT`
- Если `specs/{PROJECT}/` и `tests/{PROJECT}/` ещё нет — создать при parse/pipeline (свой INDEX, сценарии, тесты)
- Папки этого проекта: `specs/{PROJECT}/` (сценарии + `INDEX.md`) и `tests/{PROJECT}/`
- `INDEX.md` — только название документа и карта разделов со статусами. Без «Источник», URL, логина и пароля (они из `.env`). В Meta можно оставить только браузер.
- Рекомендации для автора документа: `specs/SPEC_FORMAT.md`
- Не читать весь документ целиком — работать **одним разделом** за раз
- В логах писать текущий `PROJECT`, не чужие проекты
- Таблицы сценария — обязательный источник полей и значений для каждого набора данных. Не исключать поля и проверки на основании предположений. Если таблица не попала в Markdown, прочитать её в соответствующем разделе исходного документа.
- Каждое указанное поле заполнять или проверять согласно режиму. Если поле не найдено, тест должен завершиться ошибкой с названием поля и шаблона, а не молча пропустить его. Расхождения UI со сценарием фиксировать явно; не менять требования ради зелёного прогона.

## Браузер
- Для разведки UI использовать Playwright
- Режим окна из `.env`: `HEADLESS=FALSE` (видно окно) или `HEADLESS=TRUE` (без окна)
- HEADLESS обязателен для всех запусков, включая временные исследовательские скрипты и CLI. Не переопределять его для диагностики; при ограничении заданного режима сообщить о нём, а не переключать режим.
- При `HEADLESS=FALSE` — `headless=False`, `args=["--start-maximized"]`, `browser.new_context(no_viewport=True)`. Не использовать фиксированный viewport для видимого окна.
- При `HEADLESS=TRUE` — `headless=True`, без окна браузера; запрещены `--headed` и `headless=False` в исследовательских скриптах. Настройки брать из окружения по тем же правилам, что `tests/conftest.py`, не зашивать режим в код.
- **Всегда** закрывать браузер в `finally` / `browser.close()`; не оставлять окна после скрипта
- Для ручных проверок через `node -e` / bash — один browser на сценарий и `browser.close()` в конце
- Не запускать новый Chromium на каждый мелкий шаг без закрытия предыдущего

## Загрузка файлов (обязательно)
Аналог Selenium `element.send_keys(path)` — **без клика** по полю файла:

```python
# Selenium (эталон): find_element(...).send_keys(abs_path)
# Playwright:
from conftest import upload_file
upload_file(page, "files/sample.xlsx")           # весь page
upload_file(page, "files/sample.xlsx", "#upload")  # или конкретный input
# внутри: locator(...).set_input_files(abs_path)
```

**Запрещено:**
- `click()` по `input[type=file]`, по полю/dropzone «Добавить файл» / «Выберите файл» / Browse
- ручной выбор в Finder / системном диалоге

Путь — от корня репо (`files/…`); файл должен существовать.

## Тесты
- Пайплайн сначала проверяет существующие тесты каждого кейса. Если они проходят и требования не изменились, агент для этого кейса не запускается. Обрабатывай только кейс, переданный пайплайном; запрет изменения соседних кейсов имеет приоритет над общим правилом обновления раздела. При изменении общих функций нужна проверка остальных тестов. Ошибку приложения или недоступность стенда не исправлять ослаблением тестов.
- Подробные правила и базовый промпт: `specs/TEST_WRITING.md`
- В самих автотестах на один сценарий с конкретным набором параметров — максимум 2 попытки за один запуск pytest: первый запуск и не более одного повтора после сбоя. Успешный сценарий не повторять. Не умножать попытки вложенными циклами и pytest rerun; если сценарий запрещает повтор, выполнять один раз. Применять правило и к существующим тестам при обновлении раздела. Число исследовательских запусков и повторных запусков pytest при разработке этим правилом не ограничивается; внутри каждого запуска автотеста лимит сохраняется.
- При обновлении существующих тестов до исследования UI исправлять установленные расхождения со сценарием, не требующие исследования: номера шагов, лимиты ожиданий и повторов, лишние проверки. Сохранять правки по мере работы, не откладывать все изменения до завершения исследования. Затем исследовать неизвестные элементы и состояния и проверять тесты; обязательные проверки не пропускать.
- Писать тесты в `tests/{PROJECT}/` (значение `PROJECT` из `.env`)
- Организация новых и изменяемых тестов: `tests/{PROJECT}/locators/` содержит только способы поиска элементов, `tests/{PROJECT}/pages/` — методы Page Object по страницам или частям UI. Файл `test_*.py` содержит данные, шаги Allure с вызовами высокоуровневых методов и ожидаемые результаты сценария. Низкоуровневые действия Playwright и ожидания состояния UI реализуются в Page Object. При работе с одним кейсом не реорганизовывать соседние кейсы.
- Стек: Python 3.14 + **uv** (корневой `.venv`) + pytest + playwright sync_api
- Запуск тестов из корня: `uv run pytest` или `npm run test:py`
- В docstring теста указывать ID кейса: `TC-1.1 — ...`
- Шаги Allure должны соответствовать шагам актуального сценария: явные `allure.step`, названия полей/кнопок и ожидаемые состояния. Попытки группировать отдельно, диагностику сохранять до повтора. При обработке раздела обновлять оформление существующих тестов и проверять полученные Allure-результаты по `specs/TEST_WRITING.md`.
- Один раздел документа → один `test_*.py` со всеми его кейсами. При добавлении кейсов обновлять существующий файл раздела. Общие вспомогательные функции допускается выносить отдельно, без дублирования тестов.
- Общий логин/URL — через `conftest.py` / env, без новых секретов в коде
- Если в сценарии есть блок **Проверка LLM:** — UI-тест как обычно + отдельный тест с `@pytest.mark.llm` и `assert_chat_quality` из `tests/llm_judge.py`. Нет доступа к LLM → skip и тег Allure `llm-unavailable`, UI не пропускать
- `conftest.py` читает `HEADLESS`; браузер **один на сессию**, страница — на тест
- После написания обязательно прогнать pytest и убедиться, что тесты проходят
- После раздела/скрипта не должно оставаться открытых окон Chromium/Playwright

## После раздела
1. Исследовать сценарии раздела в браузере. Для всех параметризованных сценариев любого проекта сначала исследовать один представительный набор с наиболее полным набором полей и действий во всех применимых режимах. Остальные наборы сравнить по требованиям и дополнительно исследовать только неизвестные отличия; предварительно проходить каждую комбинацию не требуется.
2. Написать/обновить тесты
3. Запустить pytest по затронутым файлам со всеми предусмотренными сценарием комбинациями параметров и режимов. При падении исследовать конкретную проблему и исправлять тест без ослабления требований; представительный набор не заменяет полного покрытия.
4. Обновить статус раздела в `INDEX.md`: `todo` → `done` / `blocked`
5. Перед `done` сверить все строки таблиц с параметрами, действиями и ожиданиями существующих тестов. Наличие теста не означает полного покрытия. При дефекте приложения сохранить тест с диагностикой, указать причину в итоговом сообщении и поставить `blocked`.
